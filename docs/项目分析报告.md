> 分析日期：2026-09-14　·　代码基线：commit `e3df9d4`
> 分析方式：全量 `mvn clean compile`（BUILD SUCCESS，18 个模块）+ 源码走查 + 配置核对

## 一、总体结论

**这是一个完成度相当高的微服务电商教学/简历项目，架构选型和关键链路设计是到位的，但"安全落地"和"工程可复现性"两块明显没跟上文档的描述。**

一句话概括：**架构设计 80 分，安全实现 40 分，文档可信度 60 分。**

项目最值得肯定的地方在于它不是纯粹的 CRUD 堆砌——Seata 全局事务、RocketMQ 函数式消费 + 幂等 + 上下文透传、布隆防穿透、Redisson 锁、ElasticJob 预热这些"微服务难点"都真实落地了代码。但走查后发现，**有一条最基础的安全链路（网关鉴权 → 下游取用户身份）实际上只做了一半**，而文档把它写成了完整实现。

## 三、做得好的地方

### 1. 公共底座设计（`mall-common`）
- **统一响应 + 统一异常**三层捕获（`BusinessException` → 参数校验 → 兜底），`ResultCodeEnum` 编码分段（HTTP 标准码 / 4xxx 用户 / 5xxx 业务），规范清晰。
- 抓住了 `GlobalResponseAdvice` 对 **String 返回值需特殊序列化**这个真实坑点——说明是踩过坑写的，不是抄的。
- `GatewayExceptionHandler` 单独放网关模块（WebFlux 的 `NoResourceFoundException` 不能放 Servlet 基的 common），这个判断是专业且正确的。

### 2. JWT 体系
`JwtUtil.validateTokenWithRedis` 的四层校验（黑名单 → 签名/过期 → Redis 存在性 → 与 Redis 精确比对支持单点登录）是完整且正确的设计，"无状态 + 可管控"两条路都走通了。

### 3. MQ 消费的健壮性套路
`MqHeaderUtil` 解决"线程池无 Web 上下文导致 Feign 调用失败"是**真实生产级问题**，且文档明确标注 `finally` 必须 `clearContext()` 防 ThreadLocal 泄漏——这套路在四个 Handler 里一致落地，不是只写了一处。

### 4. 秒杀的多层防护
网关活动级限流（2000 QPS / 突发 5000）→ 布隆防穿透 → Redisson 锁保护"读-减"临界区 → Redis `decrement` 原子自减，层次是清晰的。

### 5. Seata 事务边界把握准确
`@GlobalTransactional` 全项目**只有下单这一处**，删购物车/支付故意用 MQ 解耦——这是一致性与可用性的正确取舍，没有滥用分布式事务。

## 四、问题清单（按严重度）

### 🔴 P0 — 安全漏洞，上线前必须修

#### P0-1：订单/购物车/支付/OSS 四条路由完全没有鉴权
`mall-gateway/src/main/resources/application.yml` 中：

| 路由 | 是否挂 `Auth` 过滤器 |
|---|---|
| mall-product-service | ✅ 有 |
| mall-product-service-raw | ✅ 有 |
| mall-user-service | ✅ 有 |
| mall-test-service | ✅ 有 |
| mall-seckill-service | ✅ 有 |
| **mall-order-service** (`/api/order/**`) | ❌ **无** |
| **mall-cart-service** (`/api/cart/**`) | ❌ **无** |
| **mall-pay-service** (`/api/pay/**`) | ❌ **无** |
| **mall-oss-service** (`/api/aliyun/oss/**`) | ❌ **无** |

且配置文件**没有 `default-filters`** 兜底，服务侧 `WebConfig.addInterceptors` 的拦截器注册**整段被注释**（`mall-common/config/WebConfig.java:31-41`），`AuthorizationInterceptor` 也没启用。

> **README.md 和 docs 的路由表明确写着 `/api/cart/**`、`/api/order/**` "需鉴权"——与代码不符。**

后果：任何人可匿名下单、查看/删除任意订单、操作任意购物车、调用 OSS 上传。

#### P0-2：下游从未消费 `X-User-Id`，存在越权（IDOR）
全 `mall-service` 目录下 `@RequestHeader` / `X-User-Id` 出现次数：**0**。

网关辛辛苦苦注入的 `X-User-Id` 没有任何服务读取。订单查询的用户身份来自**前端传入的参数**：

```java
// OrderQueryDTO：userId 由客户端提交
public Result page(OrderQueryDTO query) {
    return Result.success(orderService.page(query));
}
// OrderInfoServiceImpl：直接拿这个 userId 查库，无归属校验
if (query.getUserId() != null) {
    queryWrapper.eq(OrderInfo::getUserId, query.getUserId());
}
```

配合 P0-1（无鉴权），**改一个 userId 参数就能遍历所有人的订单**；`DELETE /order/remove/{orderId}` 同理可删任意订单。

文档里写的"下游 `@RequestHeader("X-User-Id")` 取当前用户"是**设计意图，不是已实现事实**。

#### P0-3：支付宝异步回调未做签名验签
`AlipayController.payNotify`：

```java
Map<String, String[]> result = request.getParameterMap();
if ("TRADE_SUCCESS".equals(request.getParameter("trade_status"))) {
    alipayService.payNotify(result);   // ← 直接信任，无 AlipaySignature.rsaCheckV1
}
```

全仓库搜索 `AlipaySignature` / `rsaCheckV1` / `checkSign`：**0 结果**。
后果：伪造一次 `trade_status=TRADE_SUCCESS` 的 POST 即可把任意订单置为已支付。

#### P0-4：AES 密钥硬编码
`mall-common/util/EncryptHandler.java:15` → `private static final String AES_KEY = "BgKLBcLdAgZK7s64";`
密钥进代码仓库即等于泄露，应外部化到 Nacos / 环境变量。

### 🟠 P1 — 正确性与一致性问题

#### P1-1：秒杀"预扣库存"与"真实扣库存"是两套，无事务绑定
秒杀服务在 Redis 扣 `seckill-{activityId}-{skuId}`，成单时订单服务通过 Feign 扣的是 **MySQL**，两者之间没有 RocketMQ 事务消息或最终一致补偿。预扣成功但下单失败 → 少卖；下单成功但预扣丢失 → 超卖。

#### P1-2：订单超时关单能力"实现了但没接线"
`MessageSendServiceImpl.sendOrderCheckMsg`（延迟消息 `DELAY=5`）和消费者 `OrderPaymentCallbackVerifyHandler` 都已写好，但**下单链路 `OrderServiceImpl.create` 从未调用它**。
后果：未支付订单永远不会自动关闭、库存永不回滚。

#### P1-3：网关在响应式线程上做阻塞 Redis 调用 + JWT 解析两次
`AuthGatewayFilterFactory` 每个请求都执行 `jwtUtil.createTokenAndStore(...)`（阻塞式 Redis 写），且 `validateTokenWithRedis` + `parseToken` 把同一个 JWT 解析了两遍。这是 WebFlux 的**响应式反模式**，高并发下会阻塞 event loop。

#### P1-4：端口冲突
`mall-es-service` 与 `mall-pay-service` 均为 9006，同时启动必冲突（文档已知，但未修）。

#### P1-5：布隆过滤器误判率 0.1 偏高
`application-dev.yml` 配置 `falseProbability: 0.1`。布隆只会**误放行**（把不存在的判成存在），不会误杀合法请求——所以 10% 的无效 key 会穿透到 Redis/DB，防穿透效果打九折。生产建议 0.01。

#### P1-6：`deleted` 字段不是逻辑删除
`deleted` 是普通 Integer 字段，**未标 `@TableLogic`**，"删除"是否为物理删除需逐处确认。

#### P1-7：项目无法开箱复现
- 仓库内 **0 个 .sql 文件**，建表脚本缺失；
- 数据源、MyBatis、Sentinel、JWT 等大量配置托管在 **Nacos**，仓库内无导出/备份；
- 中间件地址硬编码为内网 IP `192.168.150.101`（Nacos/Redis/RocketMQ）。

新人 clone 下来**跑不起来**——这是教学/简历项目最伤的一点。

## 六、修复优先级建议

**第一批（安全，1～2 天）**
1. 给 `order` / `cart` / `pay` / `oss` 四条路由补 `Auth=` 过滤器，或改用 `default-filters` 全局兜底 + 白名单。
2. 下游统一从 `@RequestHeader("X-User-Id")` 取身份，**禁止**用前端传入的 userId 作为查询条件；`page` 强制用网关身份覆盖，`remove/{orderId}` 增加归属校验。
3. `payNotify` 增加 `AlipaySignature.rsaCheckV1` 验签。
4. AES 密钥迁到 Nacos / 环境变量。

**第二批（正确性，3～5 天）**
5. 用 RocketMQ 事务消息或本地消息表把"秒杀预扣"与"下单真实扣减"绑定，加对账补偿任务。
6. 下单成功后调用 `sendOrderCheckMsg`，接通超时关单。
7. 网关 token 续期改为 Redis 续期（不必每次重签 JWT）；或把阻塞调用切到 `Schedulers.boundedElastic()`。
8. es / pay 端口改为不冲突（如 es 改 9010）。

**第三批（工程化，1 周）**
9. 导出 Nacos 配置到 `docs/nacos/` + 补 `sql/` 建表脚本 + `docker-compose.yml` 起中间件 → 让项目能 `clone 即跑`。
10. 清理父 POM 依赖、移除 junit 3.8.1、统一 MySQL 驱动坐标。
11. 要么实现 `mall-AISearch-service`，要么从 `mall-service/pom.xml` 的 modules 中摘掉，避免"看起来有、实际没有"。
12. 修订 README / CLAUDE.md 中与代码不符的描述。

## 七、面试答辩提醒

如果这是简历项目，以下几点建议：

- **可以讲**：Seata 事务边界的取舍、MQ 上下文透传这个真实难点、布隆+限流+锁的秒杀分层、购物车选 MongoDB 的理由。
- **主动承认**（比被问出来好）：秒杀两套库存无事务绑定、超时关单未接线、回调未验签。
- **绝对不要讲**："订单/购物车有完整的鉴权和越权防护"——代码不支持这个说法，一问就露。
- 建议把上面 P0 的修复**真的做掉**，这会比文档里多写十个技术名词更有说服力。
